# Atomic Design for Agent Commander

A worker can appear on the wall, in a focused terminal, and in a picture-in-picture (PiP) request at once. All three must agree on which worker is running, who can type, and whether an answer was delivered. That is the practical reason to atomize this cockpit. The implementation should allow a developer to track a control in any of its 28 concept frames back to a shared component or a standard macOS control, its data contract, and the behavior it promises.

This is an implementation design for the macOS 26+ MVP. The gallery and tokens are review artifacts. Keep Commander’s token definitions, component source, fixtures and previews in the Agent Commander repository so a single checkout can build and review the interface. The component names below are proposed names for the native implementation. [MVP plan](../../MVP-PLAN.md) · [Concept gallery](../concepts/index.html) · [Design-system specimen](index.html) · [Token definitions](tokens.json)

## What the method contributes

Brad Frost describes five complementary ways to look at an interface. An **atom** is a basic usable element, such as a button. A **molecule** combines elements to do one job, such as an input with a label and a submit button. An **organism** forms a distinct region of an interface using smaller components. A **template** defines how regions and content fit together. A **page** populates a template with specific content, allowing the team to judge how the design behaves under realistic conditions. Teams work across the five stages in both directions. A long worker name on a finished page can reveal a flaw in a small component. [Brad Frost, *Atomic Design Methodology*](https://atomicdesign.bradfrost.com/chapter-2/)

Frost’s pattern library gives designers and developers a common reference for components in use. His workflow starts from concrete interfaces and his maintenance approach keeps the library connected to the product as it evolves. For this project the existing gallery provides the inventory, SwiftUI previews can become the living library, and a full page provides the test of whether a component change still serves the workflow. [Tools of the Trade](https://atomicdesign.bradfrost.com/chapter-3/) · [The Atomic Workflow](https://atomicdesign.bradfrost.com/chapter-4/) · [Maintaining Design Systems](https://atomicdesign.bradfrost.com/chapter-5/)

Atomic Design addresses UI composition. GoF Command and Adapter address how Commander executes operations and integrates providers. EIP correlation identifiers associate replies with pending requests. Atomicity of a database update and “atoms” in state-management libraries describe still other concepts. A visual atom can use ordinary native state, and an organism can emit one domain command. These are independent design choices. [Pattern assignments in the MVP plan](../../MVP-PLAN.md#patterns-with-specific-jobs)

The live cockpit toolbar composes the native adapter-update button and a popover of version rows. The catalog feed owns the subscription and supplies the rows in adapter order. The control appears after an explicit verified refresh and clears when the user applies the release.

## The component vocabulary

| Level | Commander examples | Implementation responsibility |
| --- | --- | --- |
| Foundations | Foreground, focus and attention colors, system and monospaced type roles, spacing, the navigation material, the terminal fill | Tokens describe values and semantic roles. Styles resolve these against system settings. They do not own a view, a subscriber or an action. |
| Atoms | Native button, symbol button, disclosure indicator, status label with a symbol, text field, text selection, divider handle | Use the native element directly where it already supplies the behavior. Give icon-only actions an accessible name. Expose a keyboard path for resizing. |
| Molecules | Worker identity with host and worktree, connection indicator with last-seen time, filter clause, host capability row, labeled field with validation, input ownership and handback control, request reply | Combine the pieces required for one understandable interaction. Preserve the target, instruction, disabled reason and accessible value as the rendering changes. |
| Organisms | Worker tile, nested worker group, coordinator console, worker wall, attention stack, queue, settings form, checkout comparison, integration attempt inspector, transcript results, host and provider lists | Present a coherent activity. Compose smaller elements and terminal surfaces. Own local presentation state such as expansion or scroll position. |
| Templates | Coordinator split, collection with inspector, task sheet, settings split, recovery detail | Give regions stable positions, resizing priorities, focus routes and overlay anchors. Multiple templates can appear together, such as a task sheet above the coordinator split. |
| Pages | A specific coordinator with five workers, a new PiP over the currently controlled worker, a failed combined test, a reconnect with an uncertain reply | Exercise the same production compositions using identified, representative data. Pages carry sample actors, hosts, events and outcomes in previews. |

A named Swift type earns its place through a shared behavior, a meaningful platform boundary, or a layout with its own invariant. A single native label, a spacer, a decorative stroke, a terminal cell and an arbitrary horizontal stack rarely need Commander wrappers. A genuinely unique integration form can remain composed in its feature until a second use or a concrete maintenance problem justifies extraction.

## Native composition and ownership

The focused native terminal window reuses the existing console title bar and surface. `NativeTerminalWell` is the AppKit leaf for a read-only SwiftTerm grid, and `NativeTerminalHeader` combines worker identity with detach, reconnect and close. The `NativeTerminalViewer` organism receives the attachment state from `NativeTerminalViewerModel`. The existing console display menu opens the matching worker’s window by value. [Terminal well](../../Sources/AgentCommander/NativeTerminalWell.swift) · [Window components](../../Sources/AgentCommander/NativeTerminalComponents.swift)

Inline terminals on the coordinator, wall, focused worker, and PiP use the same `NativeTerminalWell`. `ConsoleScrollback` selects the surface, and `NativeTerminalSlot` keeps the transcript available when attachment is unavailable or the viewer detaches. The shared mode and connection state follow the worker ID. Each visible terminal owns its own read-only, size-neutral attachment. The title bar stays with the containing console, and reply and approval controls remain in their existing places.

**SwiftUI owns the cockpit.** Use native navigation, split views, menu actions, controls and keyboard commands. Apply the dark glass material to navigation and floating controls. Keep terminal wells and long-reading surfaces opaque so an ANSI error or a selection stays readable over changing content. Resolve the reduced-transparency, increased-contrast and reduced-motion settings independently. A material belongs to its region or container, so assembling a row of buttons does not multiply glass layers. Native system materials respond to their surroundings. The HTML specimen approximates those materials for review. [Apple Human Interface Guidelines, Materials](https://developer.apple.com/design/human-interface-guidelines/materials) · [Commander materials and accessibility roles](tokens.json)

**AppKit owns the interactive terminal surface where needed.** Host the chosen terminal renderer with `NSViewRepresentable`. Treat `TerminalWell` as one composable leaf from SwiftUI’s perspective. Internally it may have a parser, cell grid, scrollback and native input client. Let the renderer handle IME composition, selection, paste, control sequences, alternate screens, and first-responder changes. The renderer must also expose readable terminal content or an accessible transcript alternative. Prototype a full-screen TUI and large scrollback before choosing the library. [Apple, NSViewRepresentable](https://developer.apple.com/documentation/swiftui/nsviewrepresentable)

Attach each projection to the same terminal identity and output stream through the API. Identify the pane by host, tmux server instance and pane ID, and retain the assignment ID across retries and handoff. The tile, PiP and focused view may each display that pane. The active interactive viewport controls terminal geometry. Passive previews render snapshots or clipped output and cannot resize the underlying pane. Share the pane adapter and screen model across distinct projection views. A native input router accepts terminal input from at most one view per pane. It checks that view’s pane binding and AppKit first responder against the confirmed lease and stamps each input intent with its control generation. The executing host validates that generation before delivery. [tmux control mode](https://github.com/tmux/tmux/wiki/Control-Mode)

| Boundary | Owns | Example |
| --- | --- | --- |
| Native elements and styles | Drawing, accessibility semantics, native activation | A handback button exposes the same action to pointer, keyboard and VoiceOver. |
| Reusable components | A small presentation model and targeted intents | `RequestReply` receives a named request and permitted response types. It emits the request ID and answer. |
| Feature model | Subscriptions, data mapping, drafts and presentation state keyed by stable IDs | A wall restores the worker selection, group disclosures and scroll anchor after zoom. A draft in PiP belongs to its request. |
| Go service and providers | Conversation and worker identity, capabilities, live terminal data, owner, policy, command acceptance and outcomes | Only the owning coordinator can direct a worker. A peer may read the transcript and ask its owner a question. The service revalidates execution-time permissions. |

Lower-level components receive values and emit intents. They do not discover tmux sessions, run SSH commands, select a provider or read a global “current worker” at send time. Keep access to the versioned API in the feature/service layer. MCP, CLI and desktop use the same operation and event contracts. The terminal’s interactive input path uses the API as well. Remote Linux and Mac hosts need the service/helper or supported SSH path. SwiftUI, glass materials and AppKit belong to the local Mac shell.

## Variants and state

`WorkerTile` composes the `ConsoleTitleBar` and transcript molecules, status, available actions and `InputOwnership`. It shares the single-line title bar with the coordinator console and PiP. The title bar combines the provider avatar and `PlatformMark` atoms with the pane title, execution host and relevant branch or lineage. Its fixed height aligns scrollback across the worker wall, and its help and accessibility label retain the full identity as the visible layout condenses. `TranscriptView` renders structured messages and uses `TranscriptToolRow` to disclose tool results. `TerminalWell` is the fallback for stored plain-text consoles. The `ConsoleSurface` modifier supplies the square shell. `AttentionGlow` marks waiting surfaces without changing their layout, and the footer identifies the pane with keyboard focus.

For local Claude ACP workers, wall and focus share the `ClaudeProgressStatus` molecule. Compared with the original wall and focused-worker concepts, the added strip sits directly above the existing task and input status. The headless 300-point tile wraps a long phase, timestamp and age above **Inspect source** when progress is unknown. The focused view fits them on one line.

`ProviderAvailabilityNotice` uses the same lower status area above Claude progress. In the narrow worker tile, restart details and the passive terminal and source actions can wrap. The exited notice sits above the still-visible completed turn. During reconciliation, the reserved-input cue shows that the developer’s lease is held while controls wait for the original turn to be verified.

`ConsoleScrollback` selects the reading view for the worker shown by each projection. In Pretty mode, `PrettyConsoleView` composes user turns, assistant Markdown blocks, selectable raw output and the shared `TranscriptToolRow`. Console and Pretty both take a tool row's state from the one `ToolStatus` mapping of its `ToolResult`: running, done, failed, declined, cancelled or interrupted. A result that arrives without its call and carries an error shows the shared `ToolResultStatusLine` above its output in both modes. The title bar’s `ConsoleModeTitlebarControl` changes one worker, and the window toolbar’s `ConsoleModeGlobalMenu` sets the mode for all workers. Both read the launch-scoped `ConsoleModeStore`.

Both reading views join compatible assistant chunks in order. Pretty places prompts in trailing bubbles and assistant Markdown in a leading column. Adjacent status and diagnostic rows form a `ConversationActivity` run, drawn by `PrettyActivityRun` as visible lines in place, never collapsed behind a count. Each line is a `PrettyActivityRow` molecule: a symbol, a compact label and the event's full readable detail, wrapping on every surface including the PiP, which scrolls. The `ActivityEvent` value names it from the transcript's existing routing (ACP kind, summary, relayed `[Provider …]`/`[Service …]` markers); an unknown kind shows its own text, and a record with only fields says so and keeps its fields action. Harness stderr and permission events use the attention ink. An activity line never holds a reply: a pending request is answered only in its `PrettyRequestForm`. The shared `RecordDetailHost` opens the underlying messages and tool results in `RecordFieldsPanel`. `PromptAttachmentHost` binds a user entry’s attachment button, including a media-only prompt’s, to that worker and its prompt. A live prompt reads its turn’s ACP parts; a recovered Claude or Codex prompt reads its one owner record from provider history, decoded by the `ProviderPromptMedia` value layer, and keeps its text exactly as written. `PromptAttachmentsPanel` labels which of the two it shows. Its panel uses the same image renderer as the worker source inspector. The incremental workspace reducer owns event ordering and the feature models own history reads. [Native conversation verification](../verification/incremental-native/README.md)

Commander activity: Pretty reads Commander's own MCP calls as purposeful activity, on every surface that draws `PrettyConsoleView` (coordinator, wall tile, focused worker, PiP). The `CommanderTool` value catalogues every `commander_*` registration in `internal/mcpbridge` (server, scoped, network and frontend registers: 20 tools) with a label, a domain symbol and the argument and response fields it summarises; a test fails if the bridge and the catalog differ. `CommanderPayload` reads arguments and results through MCP wrappers. `CommanderActivity.items` is the small pure projection: it groups calls into `CommanderWorkflow`s only on proof (the exact full request ID for ask, wait, reply and reconcile; the exact operation ID for network submit and receipt; the exact full revision for a commit and its result; a result joins a question only by explicit request ID or when it is the one already-answered question of its uninterrupted turn) and leaves every other entry in place and order. `CommanderActivity.annotate` adds the run's current request, follow-up and integration state by exact ID from the existing projection, without polling. A completed poll whose request is still pending reads as waiting for reply.

Activity stories: each workflow, and each recognised provider tool call, is drawn as a narrative card that tells the story instead of listing tools. The value layer is `ActivityStory` (`ActivityStory.swift`): a kind, a lead, a context line, a status, verified `ActivityMilestone`s, exact `ActivityRelation`s (request, worker, operation, revision, test, file, extension), a copyable outcome and the ordered evidence (every original entry). Specialised renderers implement one interface, `ActivityStoryRenderer`, and share `ActivityStory.assemble`:

- `QuestionStoryRenderer`: Asked; one answer milestone, from the run's record by exact ID or the call whose own record carried it, keeping its identity when the second source arrives; Request cancelled; Waiting for reply, once; Report awaiting approval (a provider permission holds it, so it has not started), Reporting and Reported to coordinator as distinct states.
- `RelayStoryRenderer`: Submitted, then a receipt only when its status changes.
- `ChangeStoryRenderer`: Committed and Reported, with the full revision, files and tests.
- `CommanderCallStoryRenderer`: every other Commander call by domain (delegation and controls, status, extensions, app tools). A completed delegation, follow-up, interrupt, stop or submission reads as Accepted until the run's record states the job's outcome.
- `ProviderToolStoryRenderer`: exact provider tool names only (read, edit, write, search, shell, web). The headline is the stated subject: the first known argument field (a file path, a search pattern or query, a URL or query, a command, with an argv joined by spaces), or a plain detail's first line. JSON without a known field and ACP placeholders such as `other` never head a story; the arguments stay in Tool details. Any other name, title or prefixed name keeps its raw `TranscriptToolRow` and its single native disclosure.

The shared assembly surfaces every failed call that no milestone states: one milestone per distinct step and error with `×n`, or, for a one-call story, at the head of its context. Repeated wait probes and repeated receipts are evidence, never milestones, and never take the lead. A terminal answer or result leads the compact card; a pending question leads with the decision needed and, when the parent knows it, who is needed. Nothing is inferred: no intent, percentage, timestamp or association that a call's own record or the run's record by exact ID does not state. Prose and diagnostics stay in place.

Queued, running, waiting for reply, awaiting approval (a provider permission, distinct from an agent question), answered, complete, accepted, partial, uncertain, failed, cancelled, declined or interrupted. Native `Button`, `Label` and `Text` serve as the other atoms. |

The parent supplies density, type size and actions. `PrettyConsoleView` passes `PrettyMetrics.toolSize` and its density. It keeps both disclosures in `ConsoleModeStore` by the story ID, which is the first call's ID, so open state and milestone identity hold as facts update. It performs each typed `ActivityStoryIntent` through the parent's own action: `focusRequest` sets the existing reply focus on the one `PrettyRequestForm` (focused worker, PiP); `openRequest` uses the wall tile's or coordinator's existing request route; `copy` uses the record access copy; `openSource` opens the worker's source inspector where the cockpit hosts one. `PrettyACPConsole` builds the `ActivityStoryContext` from what it already holds: `.form` with its reply context, or `.opens` with the tile's or coordinator's route. `ActivityStoryScope` offers a request action only for a request it names by exact ID: Reply, Choose, or Review approval for a provider permission holding one of the story's calls, only while that form can take input (online, reply not closed, no send in flight); or Open request, which stays available for inspecting a held request. A story never answers a request itself, so each request keeps one composer. The PiP's request carries `requestWorkflow`, linked over the whole transcript before the window is cut. `ConversationActivity.anchored` puts that story in place of the window's partial one, so the Ask is never lost and every window entry is still shown exactly once.

ACP Pretty: a console in Pretty whose worker is bound to a provider (ACP) session (`PrettyACPScope`) uses the `PrettyACPConsole` organism in place of `ConsoleScrollback`. It composes `PrettyRunStatusBar`, the shared `PrettyConsoleView` (with Thinking and tool disclosures), `PrettyRunningIndicator`, `PrettyEmptyConversation` and `PrettyRequestForm` from native SwiftUI controls, guided by the CopilotKit reference console. `PrettyACPMetrics` sets the inset, type and status bar for each density:

| Surface | Density | Transcript | Request form |
| --- | --- | --- | --- |
| Focused `WorkerTile` | regular, inset 21 | full | yes; the follow-up stays `TerminalComposer` |
| Wall `WorkerTile` | compact, inset 11, no session ID | full | no; the footer's `view request` opens it |
| `CoordinatorConsole` | regular, inset 17, assignment above | full | no; each `AttentionNotice` opens its request |
| `AttentionStack` (in-window and floating PiP) | pip, inset 11, no session ID or counts, 92 pt conversation | the request's recent window | yes, in place of `RequestPrompt` |

Each request therefore has one addressed form, on the surface that already owns its `ReplyContext`. Every surface reads values the cockpit already projects (`WorkerPresentation` and `RequestPresentation`, including session and `ProviderTelemetry`); none subscribes. The console never falls back to PTY output: with no events it says so. A request with service `choices` shows one native button per choice that sends the exact ID through the request's `ReplyContext`, and the free-form field only when there are no choices. Terminal, Console, and Pretty on a worker without a session keep `ConsoleScrollback`; the title bar, source inspector, footer, ownership and PiP drag are unchanged.

Resizable floating PiP: the floating panel's page (`FloatingAttentionRoot`) passes `AttentionStack` an exact `conversationHeight`. Pretty and Terminal both fill that height, and the slot keeps it before output arrives. The in-window PiP passes none and keeps the compact 92 pt. `FloatingPiPGeometry` holds the sizing rules as plain values. The default stack is twice the compact 350 × 430 pt. The minimum is 350 × 360 pt, and the maximum is the screen's visible area less 16 pt on each side. The `WindowResizeFrame` molecule lays `WindowResizeHandle` atoms along each edge and corner, just inside the card, with the system frame-resize cursors. The `ResizeGrip` atom marks the lower trailing corner. The zones emit `WindowResizeIntents`, and only `FloatingAttentionController` sets the window frame. The page reads its size and never writes it back. The chosen stack size (`attentionPiPStackSize`) is stored separately from the top-left placement (`attentionPiPTopLeft`). When a screen is too small, the panel is fitted without changing either saved value.

Provider usage: the `ProviderUsageStatus` molecule sits in the `TerminalStatusLine` of the wall tile, focused worker, coordinator and PiP for any worker bound to a provider session, in every display mode. It reads `ProviderTelemetry`, built once per projection from the worker's `telemetry` field and, for a missing reading, the newest live message carrying it. Context use (`ctx`, a limited gauge and percentage, used/size) and the latest reported input/output tokens are labelled separately; counts are never summed, and a count the provider did not report is absent. With nothing reported it says `usage —`. Exact counts are its help tag and accessible value. Live `agent_thought_chunk` messages join like reply chunks, keep their source IDs, and Pretty shows them as a collapsed Thinking disclosure.

`HarnessConsoleSurface` draws a crisp harness-colored border. `HarnessHeaderFill` mixes the same hue into a darker, flat title bar. Inside `ConsoleTitleBar`, `AgentAvatar` places a bright provider glyph on a dark plate, and the display and action controls share a contrast-aware ink. Both renderers use these components. `HarnessAccentMenu` lets the user choose or reset a color for that harness. The app’s `HarnessAccentStore` keeps named custom harnesses distinct and saves individual choices in local preferences. A waiting worker adds an inset amber line and retains its request label.

Console identity uses bundled product marks for Claude Code, Codex, Antigravity and Gemini CLI. A shell, generic MCP client or unrecognized profile uses the native terminal symbol. Accent overrides tint the mark for the same harness. [Local artwork and upstream sources](../../Sources/AgentCommander/Resources/HarnessIcons/ATTRIBUTION.txt)

A worker the service has bound to a provider session carries that session on `WorkerPresentation`, and its console offers a source inspector. The action is `ConsoleSourceMenuItems`, an item in the title bar’s display menu and in the worker’s action list, so the title bar is drawn as before and the action is the same in Console and Pretty mode. A wall tile, the focused worker and the coordinator console present the `ConsoleSourceInspector` organism in a popover from that control. The PiP stays compact: its item shows the asking worker’s console and opens the inspector there. The inspector names the worker and its session, offers the provider history, the live updates and the local journal in a native segmented control with a sentence of provenance, and lists `SourceRecordRow` molecules with paging inside the chosen source. Loading, an empty source, a failure and a reported gap are each stated in words. Text, tool summaries and file names are selectable and never links. Extension data is rendered only for known raster image types, decoded from the record on this Mac, and each row opens its original record in a bounded well with a copy action. `ConsoleSourceModel` in the feature layer owns the reading. It addresses the service by worker ID and drops any answer that no longer matches the open worker and source. The inspector sends nothing to the worker and holds no reply field, so drafts and input ownership are untouched. A worker without a session has no access value and its console is unchanged.

A bound delegated worker's action list also offers **Provider session…**, which opens the `ProviderSessionPanel` organism in a popover anchored beside the tile's action button on the wall and in the focused worker. It follows the adoption concept's detail rows: `ProviderSessionFact` molecules state history (available, after stop, unavailable), the control generation and the unresolved-delivery count; `ProviderCapabilityCheck` molecules show each negotiated capability with a glyph and text; discovery lists `ProviderSessionRow` molecules on the developer's request, with paging, an empty statement and a failure that keeps earlier pages. The bound session is marked, and a listed session is never a reattach target. The footer's single prominent action reattaches the worker the panel was opened for to its own session under the generation the panel read. With unresolved delivery it first asks for confirmation that those operations stay unresolved; nothing is sent or resubmitted. `ProviderSessionModel` owns the reads and the reattach, keeps one idempotency key for a retry of the same worker, generation and acknowledgement, and drops answers for a worker that is no longer open.

The focused follow-up's `TerminalComposer` gains `FollowUpContextMenu`, a paperclip beside **send**, when the worker's control record reports `prompt_capabilities` with file links or embedded context. **Link File in Checkout…** is offered only for a worker on this Mac and only for a regular file inside its checkout after symbolic links resolve; **Embed File Snapshot…** sends the file's contents as read now, text literally and other bytes as base64. Each selected file is a removable `FollowUpContextChip` above the field. The draft keeps its keyboard semantics, a draft without files keeps the original text request, and the whole content request is checked against the service's 1 MiB bound before it is sent. `FollowUpContextReader` in the feature layer is the only file access. In the Source inspector and the prompt's attachment panel, a recorded file link or snapshot reads as its name, address, type and size; its embedded contents are not drawn.

The same action list offers **Input requests…** for a bound delegated worker, in both the anchored `WorkerActionMenu` and the native menu. It opens the `ElicitationPanel` organism in a popover anchored beside the action button, separate from the provider-session panel, with the same header, kicker and session line. Each ACP structured request is an `ElicitationCard`: kind, `StatusLabel`, the agent's message as selectable text, the request and tool-call IDs, then either a form or an address, and `ElicitationDecisionBar` (prominent Submit or Accept, Decline, Cancel). A form's fields are `ElicitationFieldControl` molecules built from native controls in `fieldBox`: a text field for strings, a monospaced field for numbers and integers, a switch for booleans and a menu picker for text choices, each with its required mark, format or bounds, description and the problem the last Submit found. A shape Commander does not answer (a list, a nested object, a non-text choice) is explained in place; when such a field is required, or the form itself cannot be read, Submit is disabled with the reason and Decline and Cancel stay. A URL request is `ElicitationLinkView`: the checked host on its own line with a punycode chip where the service marks one, the full address in the terminal face with that host bold in the attention ink, and **Open in Browser…**, which asks for confirmation in a native alert naming the host before anything opens. Commander never fetches the address or opens it by itself, and opens only http or https addresses whose host is the one the service checked. `ElicitationModel` in the feature layer owns scope, reads, drafts and replies: it reads on opening, after each decision and every three seconds while open; it shows and answers only requests that name the open worker and that worker's own bound session, as the cockpit model knows it; form values are sent exactly as entered and numbers as the literal typed; a 404 or 409 reply reads as withdrawn, and a sent or withdrawn request does not return from a stale read.

The floating `AttentionPanel` hosts the same `AttentionStack` organism as the preview. It uses the same request queue and drafts as the main window. The panel has a bounded frame with internal scrolling, and remembers its location separately from request state. The feature layer filters duplicate automatic surfaces when the source pane is visible. The window host handles placement and activation.

Use explicit presentation variants for wall density, a focused worker, and a passive preview. Availability comes from advertised capabilities and actor permissions. A provider name supplies attribution and diagnostics. It should not select the tile implementation. An unrecognized client with MCP can still have a named assignment, results and a tile. The tile explains any unavailable approval or input path.

Keep task progress, connection, attention, input owner, message delivery and keyboard focus as independent dimensions. For input ownership, distinguish the identified actor holding the lease from an in-flight attempt to take or return control. Selection and scroll position belong to the presentation. A worker may be working, disconnected, awaiting an answer and still assigned to the developer. Show the last known timestamp, the pending question and the held control separately. A checkmark for acceptance says the service received an answer. Worker delivery and resolution require their own evidence. [State vocabulary](tokens.json)

A disconnected worker keeps its last output and its pending request. `TaskState.disconnected` is read before the pending request, so the `TerminalStatus` atom shows `! disconnected` on the wall tile, the focused worker and the PiP status line, and `StatusLabel` shows it in the side panel and on a collapsed group. `ConsoleNotice` prints the service’s explanation in amber. `RequestReply` keeps the draft, disables the field and the send action, and states that the reply waits for the host to reconnect. Its help tag and accessible value carry the full reason. The concepts draw the disconnected label with a neutral dot ([09 All agents](../concepts/index.html#all-agents)). The cockpit uses the attention ink for it, as the hosts page does, because the worker’s amber request outline remains. An accepted answer with unknown delivery appears as `reply <id> delivery unknown` in the focused worker’s status line.

A worker in the opt-in persistent SSH mode keeps running on its Linux host when the link drops. The API reports this as `connection: "reconnecting"` on the worker, and `state` stays the worker’s own turn state. `WorkerPresentation.hostIsReconnecting` and `RequestPresentation.hostIsReconnecting` carry it to the components. The `HostLinkStatus` atom draws `↻ reconnecting` in the attention ink after `TerminalStatus` in the shared `TerminalStatusLine`, so the wall tile, the focused worker, the coordinator console and the PiP agree. Its label style sits beside `StatusLabel` in the side panel, the attention queue and a collapsed group. A narrow tile keeps the mark alone. The help tag and accessibility label name the host. `RequestReply` stays enabled and adds one line above the prompt, `↻ reply now · held until <host> reconnects`. The full statement is that line’s help tag and accessible value and the hint of the field and send action: Commander keeps one answer and the worker reads it when the link comes back. The cockpit announces that statement once per request. A connected worker shows nothing new. The SSH-only disconnect above is unchanged and takes precedence if both are reported.

**Worked interaction.** The developer controls worker A in the coordinator split. Worker B from another run asks a question.

1. A request event creates one PiP entry keyed to B’s request. Its heading names the project, run and worker. It arrives at the bottom right of the worker region. Focus and input ownership stay on A. A quiet accessibility announcement identifies the waiting question.
2. Activating the PiP reply field moves keyboard focus into that field. Its `RequestReply` binds the draft to B’s request and sends one structured answer through the API. It needs no terminal input lease. The same component can appear in the queue, side panel or focused view. A resolved request displays the existing resolution, even if another surface submitted it.
3. Expanding B shows its terminal alongside the coordinator. To type into B’s live terminal, the developer explicitly takes control. `InputOwnership` shows acquisition in progress and enables terminal input when confirmed. A coordinator command queued earlier must pass the ownership check again at execution. External clients attaching directly to tmux remain outside Commander’s control guarantee.
4. Closing the PiP restores the previous focus when that target still exists. A retained terminal lease on B persists across zoom, closing the PiP and reconnect. Explicit handback releases it. An ambiguous response after SSH loss displays its operation ID and delivery uncertainty. An automatic retry needs verified duplicate protection.

## Verification and evolution

Implement the components for the first live coordinator, worker wall and PiP reply as those features land. The full inventory maps the concept direction into reusable pieces. Expand previews and cover the scenarios below incrementally as the corresponding views become usable.

- **Component previews.** Exercise long host aliases, identical worker names in separate runs, nested assignments, a non-Git project, an unavailable capability, an empty queue, a closed worker and a missed-history interval. Give a truncated identifier an accessible full value. Test narrow and wide windows, independent text scaling and all three system appearance preferences individually and in combination.
- **Native interactions.** Test keyboard-only traversal, resizable split and scrollable wall, return focus after zoom, VoiceOver reading order, button names and field errors, and text and symbol cues alongside color. VoiceOver should hear an escalation once. Provide explicit access to the transcript without announcing every streaming line. Verify the opaque fallback, actual native material and ANSI readability on the Mac in addition to reviewing concept screenshots.
- **Target and state correctness.** Exercise two replies from different surfaces, a lease change while an action is queued, a PiP arriving during IME composition, a recycled tile, and reconnect after reply acceptance. Verify the intended recipient, duplicate handling and preserved ownership against the real API. Verify structured conversation submission with dollar signs, quotes, code fences and multi-line text.
- **Scale and fidelity.** Exercise three coordinators with ten workers each. Send high-volume output from one pane while responding to another. Check that the same pane remains legible in multiple projections, the active terminal survives a layout change, a hidden preview cannot resize it, and a burst of output cannot delay the approval interaction. Exercise both Linux and Mac SSH hosts, persistent-helper and SSH-only modes.
- **Library stewardship.** Implement the first vertical slice through wall → PiP → answer → return. Give a shared component a named owner and production-backed preview when its behavior changes. Review the affected page fixtures and an accessibility variant before publishing a breaking change to the component’s interface. Retain unique screen-level compositions while their content or workflows are still changing.

The payoff is one fix for reply routing, ownership cues or focus restoration across several views. The costs are extra interfaces, catalog upkeep and the risk of hiding platform behavior behind wrappers. A useful review question is whether editing the shared component would improve every consumer. If a new mode changes authority, semantics or target routing, model that behavior explicitly. If it only changes the position of an existing interaction, reuse the component and change the template.

A future web or cross-platform cockpit can reuse semantic token names, request and ownership contracts, fixture data, page scenarios and accessibility expectations. Its renderer and platform controls can implement those contracts independently. For the first source-built Mac release and later signed download, the review target is the behavior of the native Mac application.
