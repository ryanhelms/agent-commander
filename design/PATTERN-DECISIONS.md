# Agent Commander pattern decisions

Use this record before implementing each change. Begin with the user-visible behavior and the failure the design must prevent. Select a Gang of Four (GoF) pattern for a recurring collaboration between components, or an Enterprise Integration Pattern (EIP) for a message exchange with delivery consequences. A direct function, query, or state transition is also a design decision. [GoF catalog and applicability](https://www.informit.com/store/design-patterns-elements-of-reusable-object-oriented-9780201633610) · [Enterprise Integration Patterns catalog](https://www.enterpriseintegrationpatterns.com/patterns/messaging/)

The Go service owns domain operations. The native SwiftUI/AppKit cockpit, terminal client, Go CLI, and Go MCP server reach it through one versioned API. Go host helpers on macOS and Linux can execute work delegated to them under a run’s policy. The product serves one developer across a Mac and enrolled SSH hosts. Each row names the component responsible for the behavior. Milestones M1–M6 follow the [MVP plan](../MVP-PLAN.md).

## First usable run

After visual approval, start with the local Mac and one supported provider. Have a coordinator delegate a real task through MCP, watch its live tmux worker and answer a question from the cockpit through the API. Add a second worker on the same path to exercise the live wall while replying to the first. Use this version for a real task as soon as the reply reaches the intended worker and request exactly once under a repeated click, and typing resumes at the expected keyboard target. If delivery is uncertain, show that status and keep the original reply available for reconciliation.

Use what happens in that session to choose the next increment. A second provider, broader adoption, saved views, SSH continuity, Git integration, and historical search can each be added and exercised when their flows are ready.

## Before coding a change

The 15 flow decisions below already provide the pattern analysis. Before writing code, consult the row that applies. Use its decision directly when it fits. For a new flow or a change of approach, one sentence in the current work item can name the choice and the problem it solves. For example, “Bind replies to the question ID so changing focus cannot redirect an answer.”

## Adoption status

- **Use as the corresponding flow ships.** The GoF Facade, Adapter, Command and identity-resolution Strategy correspond to actual API, provider, retry and repository variations. EIP Request-Reply, Correlation Identifier, Idempotent Receiver, Publish-Subscribe Channel and Message Store describe MVP delivery and persistence guarantees. Atomic Design organizes the app’s component inventory. The direct policies and state transitions identified below also ship in the MVP.
- **Conditional within the MVP.** Apply EIP Process Manager to adoption or integration when asynchronous replies and branching participants require a coordinator. Use a Messaging Gateway where a domain caller needs to abstract a real messaging boundary. Reassess GoF State, Composite or additional Strategies only when a row’s trigger appears.
- **Deferred.** An external broker, replay of the entire event history to reconstruct domain state, and distributed transaction coordination each require independent evidence that the per-user service cannot meet a measured need.

Go structs and functions can express these collaborations. | The same scoped mutation through MCP and CLI receives the same acceptance, refusal, or continuation. ## Host, provider, and worker boundaries

| Flow and owner | Design choice and reason | Simpler alternative or trigger for more | Scenario to exercise with this flow |
| --- | --- | --- | --- |
| **Host enrollment and execution** · Go host adapter and enrolled helper | Use GoF Adapters for local execution, persistent SSH helpers, and SSH-only hosts. Report host capabilities explicitly. Choose disconnect behavior per run and validate that its participating hosts can carry it out at launch. Pass conversational content as framed data. | A direct capability check and selected transport suffice. A deployment-wide router or broker would add another failure boundary. | Sleep the Mac. A remote run with the necessary helper can continue under its policy. An SSH-only host reports what can be recovered and which actions must await reconnect. Multiline shell metacharacters arrive literally. M1, M4. |
| **Discovery, launch, and adoption** · Go provider adapters | Adapt each provider’s actual evidence for pane association, session identity, pending approvals, and capabilities. A supported live association can attach in place. An automatic process handoff requires an idle worker and proof that the same conversation, history and pending work survive. Resume from recorded adoption checkpoints after interruption. | A generic executable profile and cooperative MCP inbox cover launch and messages. Add a new provider adapter for independently verifiable features such as answering a native approval. Matching by directory is a discovery hint. | Discover two processes in one directory, including a busy one. A verified association selects the correct conversation. An ambiguous match stays view-only with an explanation. A plain MCP client can still coordinate and report a result. M1, M6. |
| **Smart groups and lineage** · Go project catalog and queries | Persist explicit assignment, run, parent, host, and conversation IDs. Use GoF Strategy for repository-identity resolution when Git metadata or an explicit checkout link supplies different evidence. Saved views filter by metadata independently of lineage. | Use composable predicates for ordinary directory, host, client, or status filters. A new strategy is warranted when the algorithm or its evidence changes. | Two runs share one repo. A worker changes directories and moves into a different smart view while its parent and controlling coordinator stay the same. Ambiguous remote checkouts require an explicit link. M2, M3. |
| **Delegation and launch retries** · Go assignment service and executing host | Use GoF Command and EIP Idempotent Receiver. Reserve the assignment ID and worker slot atomically before launch. Bind the caller’s retry key to its intent and result. The host tracks the launch by assignment ID and reconciles a missing acknowledgment. [Idempotent Receiver](https://www.enterpriseintegrationpatterns.com/patterns/messaging/IdempotentReceiver.html) | A direct launch is sufficient inside the executing host only after the assignment is reserved. Reuse of the same key with different intent is a distinct error. | Interrupt the connection after process start. A retry addresses one worker, tile, and slot. Concurrent nested launches respect the run limit. M1–M4. |
| **Inbox, questions, approvals, and results** · Go conversation service | Use a durable addressed inbox and EIP Request-Reply. A reply references the initiating message or approval using a Correlation Identifier. Parent and run IDs describe membership. A scope-checked actor answers a specific outstanding request. [Request-Reply](https://www.enterpriseintegrationpatterns.com/patterns/messaging/RequestReply.html) · [Correlation Identifier](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CorrelationIdentifier.html) | A direct result suffices for an immediate API query. A generic MCP worker can use bounded inbox waits with a cursor. A provider-specific wakeup is optional. | A worker has two questions open. Answer one and verify that the other stays pending. Repeat the original reply and recover the recorded resolution. M1, M2, M6. |
| **Delivery uncertainty and human continuation** · Go operation service and provider adapter | Persist an operation ID, acceptance, evidence of delivery, completion, and typed outcomes. Reconcile after a lost receipt using provider or inbox evidence. A `requires_user_action` result identifies the prompt and how to resume after verification. If evidence is insufficient, expose `delivery_unknown`. An adapter that lacks the operation returns `unsupported_capability`. Each outcome identifies the worker, reason, safe continuation and status lookup. Bootstrap and service recovery can start the API, after which domain work resumes through it. | One operation row and a guarded transition are enough. Use EIP Process Manager only for workflows that must coordinate multiple participants or choose the next action after asynchronous evidence arrives. | Lose SSH just after an approval response. Reconnect and inspect the original operation without duplicating the response. Provider sign-in resumes the original caller’s operation. M1, M4, M6. |
| **Authorization and explicit handback** · Go service and the host that executes input | Use a direct policy function and durable per-worker input ownership. Verify actor, run, request scope, and current control generation again at execution. Capture the generation when queuing input so an old command cannot become valid after takeover and handback. Single-request replies preserve terminal ownership. | UI disabling provides affordance. The API and executing host enforce the decision. Use one authoritative writer for a worker’s control state. A disconnected client must reestablish that authority before accepting conflicting control changes. | The developer takes a worker from its owner while input is queued. After sleep and reconnect, the worker is still held until explicit handback. A peer run can read and ask the owner a question. Its direct interrupt is denied. M2, M4. |

## Streams, history, and Git

| Flow and owner | Design choice and reason | Simpler alternative or trigger for more | Scenario to exercise with this flow |
| --- | --- | --- | --- |
| **Stream fan-out and recovery** · Go event service, host adapters, and Swift consumers | Use EIP Publish-Subscribe Channel for independent observers of run events. Keep terminal bytes on separate bounded subscriptions. Version lifecycle events with ordered cursors within their stream. A subscriber resumes at its cursor or receives a consistent snapshot and the next cursor. [Publish-Subscribe Channel](https://www.enterpriseintegrationpatterns.com/patterns/messaging/PublishSubscribeChannel.html) | Direct subscriptions fit a per-user service. For a slow terminal consumer, resynchronize from a pane snapshot and identify any missing output. Lifecycle decisions must remain recoverable. | Flood one of 30 worker panes, then issue an approval on another. Verify responsive input, no duplicate tiles, bounded buffering, and accurate gap reporting after reconnect. M3, M4. |
| **History, provenance, and search** · Go history store | Use EIP Message Store for searchable conversation records and operation evidence. Under the project recording policy, store terminal output with timestamps, worker, host, source position, and recording gaps. Keep raw input keystrokes and hidden input out of history. SQLite transactions keep retained output, recorded metadata, and the full-text index consistent. [Message Store](https://www.enterpriseintegrationpatterns.com/patterns/messaging/MessageStore.html) | Store domain state directly. Event sourcing is a separate choice if rebuilding all state from an event log becomes a requirement. Index terminal output and preserve project access rules when querying history. | A search lands on the correct worker after its worktree moves. Expiring a transcript removes its indexed text. An SSH-only outage appears as a gap where history cannot be verified. M4, M5. |
| **Coding workspace and source snapshot** · Go Git adapter on the participating hosts | A GoF Adapter wraps Git operations. Record the per-assignment choice to use a commit, include selected working changes, or stay on the source host. Capture an immutable baseline and transfer manifest, then verify it in the worker’s linked worktree before launch. | The three choices can be explicit branches in one function. Extract a Strategy if snapshot algorithms grow independently. Keep research and review in a shared checkout when requested. | Exercise staged, unstaged, and explicitly selected untracked changes. Retry a transfer after source edits, verify the original baseline, and preserve the developer’s index. Attribute only the worker’s subsequent changes to its handoff. M5. |
| **Candidate integration and combined tests** · Go integration service and Git adapter | Persist the target revision, selected worker revisions, candidate, test evidence, and outcome. A synchronous local path uses ordered functions and checkpoints. Apply EIP Process Manager when the operation waits for remote handoffs or tests, branches on conflict or failure, and resumes a specific operation after restart. Revalidate the target and checkout before advancing to the tested candidate. [Process Manager](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ProcessManager.html) | Introduce the coordination behavior where multiple participants and recoverable decisions exist. A durable row per attempt suffices for a fixed local sequence. A distributed transaction introduces no useful guarantee around an external test process. | Fail the combined suite, produce a conflict, then advance the target concurrently. Each attempt retains its own evidence. A retry cannot publish an untested candidate or overwrite newer work. M5. |

## Optional coordinator companions

The local provider adapter discovers the Devflow UI companion through a bounded MCP tool listing in the run’s checkout. It registers the companion for a coordinator only when the restricted server advertises exactly `devflow_ui_open`. Only the coordinator’s live connection requests an automatic browser open. The discovery probe has no browser side effects. A missing executable, an older release, or a broader tool surface leaves the planning run available with its usual permissions. The service owns executable selection and passes the verified path through the private launch file. The live companion receives the socket, actor ID, scoped token and coordinator role from that job. The discovery process receives no actor binding. Commander enforces the token’s permissions on each worker activity or reply request.

These scenarios group later work by milestone. Pick the relevant case as a feature comes online and keep using the working app between increments. The local watch-and-reply run above is ready to use on its own.

| --- | --- |
