# Agent Commander pattern decisions

Use this record before implementing each change. Begin with the user-visible behavior and the failure the design must prevent. Select a Gang of Four (GoF) pattern for a recurring collaboration between components, or an Enterprise Integration Pattern (EIP) for a message exchange with delivery consequences. A direct function, query, or state transition is also a design decision. [GoF catalog and applicability](https://www.informit.com/store/design-patterns-elements-of-reusable-object-oriented-9780201633610) · [Enterprise Integration Patterns catalog](https://www.enterpriseintegrationpatterns.com/patterns/messaging/)

The Go service owns domain operations. The native SwiftUI/AppKit cockpit, terminal client, Go CLI, and Go MCP server reach it through one versioned API. Go host helpers on macOS and Linux can execute work delegated to them under a run’s policy. The product serves one developer across a Mac and enrolled SSH hosts. Each row names the component responsible for the behavior. Milestones M1–M6 follow the [MVP plan](../MVP-PLAN.md).

The local API service and multiplayer device helper each take operating-system locks on their state directory and configured socket before recovering a stale listener. Concurrent launchers join the running service, and separate profiles can run concurrently with distinct sockets.

A coordinator's private inbox uses a Message Store and a local Publish-Subscribe Channel. A durable commit wakes all local waiters for that mailbox. Periodic checks recover writes from another process and recheck enrollment and run state. Each waiter reads from its own message ID and revalidates the live binding before returning a note. A stored note never authorizes a provider turn.

The multiplayer relay pilot implements a durable delivery path. See the [multiplayer relay architecture](MULTIPLAYER-RELAY.md) for the target topology and extension contracts. A Recipient List gives each logical target an independent delivery. Competing Consumers distribute those deliveries across interchangeable dispatchers. A fenced device route directs each delivery to the edge holding its live tunnel. The [pattern library](../.context/design-patterns/index.md) describes these and their alternatives.

## First usable run

After visual approval, start with the local Mac and one supported provider. Have a coordinator delegate a real task through MCP, watch its live tmux worker and answer a question from the cockpit through the API. Add a second worker on the same path to exercise the live wall while replying to the first. Use this version for a real task as soon as the reply reaches the intended worker and request exactly once under a repeated click, and typing resumes at the expected keyboard target. If delivery is uncertain, show that status and keep the original reply available for reconciliation.

Use what happens in that session to choose the next increment. A second provider, broader adoption, saved views, SSH continuity, Git integration, and historical search can each be added and exercised when their flows are ready.

## Before coding a change

Follow the [shared pattern rules](../.codex/rules/DESIGN-PATTERNS.md) before every code change. Use the applicable decision below when it fits. For a new or changed decision, record the update here and summarize the choice in the issue or PR. For example, “Bind replies to the question ID so changing focus cannot redirect an answer.”

## Adoption status

See the [implementation evidence](#implementation-evidence) for the current code and tests behind these decisions.

- **Use as the corresponding flow ships.** The GoF Facade, Adapter, and Command describe the existing API, provider, and retry paths. EIP Request-Reply, Correlation Identifier, Idempotent Receiver, Publish-Subscribe Channel and Message Store describe MVP delivery and persistence guarantees. Atomic Design organizes the app’s component inventory. The direct policies and state transitions identified below also ship in the MVP.
- **Conditional within the MVP.** Apply EIP Process Manager to adoption or integration when asynchronous replies and branching participants require a coordinator. Reassess repository identity Strategy when independent identity sources require it. Use a Messaging Gateway where a domain caller needs to abstract a real messaging boundary. Reassess GoF State, Composite or additional Strategies only when a row’s trigger appears.
- **Deferred.** An external broker for the base local service, replay of the entire event history to reconstruct domain state, and distributed transaction coordination each require independent evidence that the per-user service cannot meet a measured need.

## Cockpit and API

The cockpit owns the per-user launch preference. The first process acquires an operating-system lock and can receive requests to reopen its window. Go services separately lock the state and socket they own. This keeps GUI activation independent of background jobs and lets each relay edge run its own instance.

A local feasibility check attached a read-only, size-neutral tmux client and an AG-UI subscriber to the same managed worker. Detaching the terminal during a turn, reattaching, and reconnecting AG-UI preserved both assistant messages and a single harness process. The fixture ran Commander's terminal runner. A native terminal view can use that PTY stream, while an embedded CopilotKit view uses the stable worker ID and structured AG-UI events. Keep the existing input grant at the Go boundary. [SwiftTerm's embeddable AppKit view](https://github.com/migueldeicaza/SwiftTerm#macos-nsview) · [CopilotKit reference client](../poc/agui-console/README.md)

An explicit catalog refresh writes its verified candidate to the same local pin record that activation and rollback replace atomically. An owner-only Publish-Subscribe Channel sends the current notice set on connection and when it changes. A refresh from another process therefore reaches an open cockpit, and a reconnect recovers a missed change. Opening the cockpit reads local pins without contacting publishers.

## Host, provider, and worker boundaries

The project catalog persists directory identity in the service and associates runs when they are accepted. Each run retains its original checkout for execution and existing authorization. The app and CLI share the API for opening folders and starting runs. Cockpit links identify saved projects or runs by ID and perform navigation only.

The independently released `agent-acp` SDK generates a GoF Facade for each supported language from its versioned session schema. Each facade delegates runtime calls to an adapter. This supplies one vocabulary for conversation operations. Provider Adapters translate its messages, request IDs and events into the protocol supported by each harness. Share the ACP transport implementation across adapters. Define the public contract in portable session terms so transport negotiation and provider-specific history readers can change independently of callers. Commander maps worker IDs to session handles and applies its ownership policy before invoking the facade.

The SDK candidate packages the same generated contract as a Go module proxy archive, an npm tarball and a Python wheel. Commander records the Go version and checksums in its module files. Its release build verifies the supplied archive with Go's checksum validation in a fresh cache. The language consumers use the same shipped conformance fixture. [SDK release verification](verification/sdk-release/README.md)

## Streams, history, and Git

The ACP Adapter uses a Content-Based Router keyed by the upstream `sessionUpdate` discriminator. A typed activity identifies the bounded workspace projection and its worker-scoped source record (Claim Check). The source observation cursor identifies the record, and the page cursor advances a history traversal. Runner uploads use Message Sequence and Idempotent Receiver: a single sender applies backpressure, retries a batch with the same identity and waits for its receipt. Native projections are volatile, while legacy output and its receipt commit together. Incremental owner subscriptions share immutable AG-UI JSON Patch frames by workspace revision. A reader exceeding the retained frames recovers with a snapshot and a gap reason. [Processor benchmarks](verification/processor-capacity/README.md)

The selected worker's private source uses a separate Publish-Subscribe feed with the same cursor epochs as paged live history. Subscribers receive bounded pages and can resume from the last delivered page. The bundled SDK retains evicted control evidence independently of ordinary output, so a known text gap can recover while an uncertain permission or turn outcome closes the affected control path.

The local cockpit feed uses a GoF Adapter and EIP Message Translator to project retained provider events as AG-UI messages. A Publish-Subscribe Channel signals committed workspace changes over the private socket. Each subscription starts with a current snapshot and sends ordered state patches. Reconnection replaces the projection with a fresh snapshot. Reply commands keep their existing Request-Reply path and Correlation Identifier.

A local ACP broker can own one adapter process for multiple tmux runners. An owner-issued, single-use launch ticket binds each runner to its exact session setup. The broker shares only compatible executable pins, checkouts, policies, credential profiles, and wire versions. It routes messages by native session identity and keeps bounded output queues per runner. Explicit prewarming uses the same broker with a separate process scope for each worker. Qualification measures the added forwarding cost as well as shared process memory.

The local Claude adapter uses a stable provider session ID and passes each follow-up through standard input. The service uses an addressed inbox as a Message Store. The receiver claims a follow-up by its Correlation Identifier under the current control generation. A caller-provided idempotency key returns the same acceptance receipt after a retry. Handoff cancels queued commands from the outgoing controller. A restart marks a claimed turn with an uncertain outcome until the original runner reports evidence. The original runner can report the outcome using the same message ID.

The worker control API supports a bounded Publish-Subscribe wait on the authenticated worker's current revision. Committed mutations wake waiting readers, and each reader compares its own control snapshot. Claims, choices, and operation receipts still use addressed Request-Reply commands. Admission checks run outside the durable command transaction. The service rechecks authorization, idempotency, and capacity before launching.

Console and Pretty share that feed. The cockpit keeps a display mode per worker ID so zoom, the wall and PiP agree even when a new snapshot replaces the worker object. Selecting a mode for all consoles sets the default and clears individual choices.

The cockpit keys persistent accent preferences by harness identity. A color change follows that harness across workers, runs and windows. Attention and keyboard focus retain their own cues.

## Optional coordinator companions

Devflow is a first-party companion in the scoped tool registry. At launch, the registry probes for exactly `devflow_ui_open` in the checkout of an interactive local Claude coordinator. The probe has a deadline and receives neither actor credentials nor the auto-open flag. The private launch record carries the versioned selection and the resolved executable path. The live harness attaches the UI-only MCP server with `--auto-open` and the coordinator's scoped credential. It can also call `devflow_ui_open` explicitly to open or navigate the console. An incompatible or missing companion leaves the planning run available. A pending job from an earlier build can use its previously verified Devflow path.

## MCP tools over ACP

The optional stateless binding adds an Adapter around the same scoped Commander tool server. Its logical request ID is independent of ACP transport correlation. The registration owns its per-request authorization, concurrency limit and cancellation. The binding replaces the local Commander MCP subprocess only when explicitly enabled and advertised by the connected peer. ## Scoped coordinator tools

The Commander API remains the Facade for brokered read tools. First-party Go code registers versioned tool descriptors and handlers at startup. An optional private `tool-grants.json` in the service state directory selects registered tool versions for an exact project path, for example `{"projects":[{"path":"/absolute/project","tools":{"connector.read":1}}]}`. A grant binds that path to its resolved directory at startup. Configuration changes take effect when the service restarts.

`commander_list_tools` and `commander_call_tool` use the existing MCP connection. The service checks the bearer against the addressed local coordinator and active run on discovery and invocation, then applies the project grant. A call validates the registered schema before running with a five-second context deadline outside the service lock. The service rechecks authorization before returning the bounded result. Provider errors return a generic failure, and tool results go directly to the requesting MCP client.

Configured tools bind their settings to each project grant at startup. Linear's Adapter passes one issue identifier and the allowed team UUIDs as variables in a fixed, filtered GraphQL query. It checks the returned issue and team again before projecting the result. The grant names a service-side key file. An absent issue and an issue outside the allowed teams have the same outcome. Unavailable credentials and upstream rate limits use fixed errors, and GraphQL partial failures withhold the result.

To add a brokered connector, declare a versioned `toolregistry.Tool` with a read action and an input schema. Supply `Run` for a handler that takes no project settings, or `Bind` to validate settings and construct a handler for each project grant. Register it in the service's `toolregistry.Load` call. The integration test registers a workspace reader alongside Linear and exercises both through the real `agentctl mcp` subprocess. The test checks discovery, project isolation, worker-role spoofing, schema validation, deadline enforcement, and independent dispatch. [Registration example](../cmd/agentctl/workspace_connector_fixture_test.go) · [Integration test](../cmd/agentctl/linear_mcp_integration_test.go)

Run the connector proof with `AGENT_COMMANDER_TEST_INTEGRATION=1 go test -count=1 ./cmd/agentctl -run '^TestLinearLookupThroughAgentctlMCP$'`.

## User plugins

User plugins extend the scoped coordinator tools without installing code in the service. A plugin is an out-of-process MCP server with a manifest. `agentctl plugin install` probes it once, freezes its tool schemas and pins a digest of its files. Installing grants nothing; `tool-grants.json` remains the only route to an agent. `internal/plugins` gives `toolregistry.Load` one registered tool per contributed tool, so discovery, authorization, validation, deadlines and result limits stay on the existing Facade path.

Each bound handler is an [Adapter](../.context/design-patterns/adapter.md) from the registry handler to MCP `tools/call`. It passes the resolved project scope and grant settings in `_meta`. One supervisor per plugin acts as a [Service Activator](../.context/design-patterns/service-activator.md). It starts the process lazily from a stripped environment without Commander credentials, verifies the digest before each start, and replaces the process after an exit or a missed deadline. A refused plugin keeps its tools registered with a fixed unavailable outcome, so its grants do not stop the service. This follows the out-of-process rule for third-party extensions in the [relay architecture](MULTIPLAYER-RELAY.md). The process boundary isolates address space and credentials but not file access; sandboxing is a later increment. [User plugins](PLUGINS.md)

## Local SDK runtime

For new built-in sessions the local launcher prefers the installed ACP adapter. A service can require ACP or select the legacy Claude runner for future assignments. A configured adapter that cannot start reports an error. The job record binds each existing worker to the executable, runner and native session selected for that assignment.

The tmux runner calls the SDK Facade for each new opted-in assignment. Its private launch record fixes the runner choice. The worker receives a scoped MCP connection. Only the trusted local runner binds a native session ID to a worker, and an existing binding is immutable. The input lease and the provider request ID address each reply. The API treats a repeated operation ID as an Idempotent Receiver and validates its intent.

Delegation accepts an optional client and falls back to the run's client. The launcher checks availability before the service reserves the worker and persists its selected client. The pinned Codex ACP adapter marks session roots trusted and merges effective MCP configuration. An isolated home alone leaves the checkout configuration in scope. Enabling managed Codex requires a launch profile that can enforce the run's tool policy before entering the requested checkout.

For the first SSH-only run, keep the controlling runner beside Commander's service and transport the remote harness's ACP stream over SSH. Give the remote MCP process a reverse Unix socket to a worker-authenticated listener. That listener requires the worker credential for all requests before executing an API operation. The desktop owner socket stays local. Use a fresh remote socket for each connection and rely on OpenSSH host-key verification. A loopback OpenSSH fixture with generated keys verified the live Claude worker, its authenticated MCP round trip, and the local and remote labels in the native cockpit. Passive history reads invoke the host-side SDK reader over a separate SSH connection using the original native handle. [SSH verification](verification/ssh-worker.md)

For SSH-only disconnects, keep the native session reference and pending question in the existing Message Store. An answered request keeps its original answer and correlation identifier, with a separate delivery status when the adapter cannot confirm receipt. The Idempotent Receiver returns the original reply receipt on an identical retry. Reconciliation correlates the exact wait invocation and its recorded MCP result in the original native history. It can confirm receipt of the same answer or preserve the unknown outcome. It leaves the original turn disconnected.

Persistent SSH is opt-in through `AGENT_COMMANDER_SSH_MODE=persistent`. It keeps the adapter process on the enrolled host and reconnects the SSH link to the same native conversation. The negotiated window retains a bounded 512 KiB of chunks and uses independent cumulative acknowledgments for input and output. Legacy peers use the single-chunk protocol. Input is acknowledged after the original adapter receives it. Transport cursors live in memory, so losing either endpoint requires native-history reconciliation. The reverse MCP socket reconnects to the worker's existing API authority through a separate connection. [Window and acknowledgments](../internal/sshlink/window.go) · [Reconnect tests](../internal/sshlink/link_test.go)

For coding workers, a Git Adapter provisions a linked worktree from a particular commit and reports the assigned branch and path. Integration prepares a detached candidate worktree at the recorded target revision, merges the selected worker revisions there, and runs the chosen combined test command. The coordinator's branch advances only after successful tests and a fresh target revision and checkout check. Use a Message Store for the integration operation and its outcome so an identical retry can recover a result without rerunning tests or moving the branch twice.

The Claude CLI initializes `--resume` for the exact UUID and checks the provider-reported ID when a new turn begins. Older CLI coordinators can recover the binding from a unique local journal that matches the original assignment and includes the authenticated Commander status result for that run. Reattachment uses the owner's next explicit follow-up and retains the coordinator's existing tool policy.

## Multiplayer workspace membership and combined view

Leaving a workspace removes the member from that workspace only. The relay records the departure in `mp_workspace_departures` and ends the member's live claims there. Group membership and the group's other workspaces stay unchanged. Every workspace read skips departed members. Only the group owner restores access, by removing the member from the group and adding them again. The workspace owner cannot leave.

The combined view is an Aggregator over two sources. The first is agents the member published that the caller may already see: their own, those shared with the group, or those visible to the caller as a friend or grantee. The second is holders of live claims in the workspace. The relay does not join another member's agents to that member's claims, so one worker can appear twice. The caller's own device agent joins the caller's agents to their claims. Fields with no source stay empty and are never inferred: branch and check counts.

## Opening a window page

The network tray opens a main-window page through one Command. `CommanderOpenRequest` is the command as a value: a place ID, and optionally a server and an item on that place. `CommanderWindowRouter.open(_:)` is its only receiver. It brings the cockpit forward through `SingleInstanceCoordinator`, which reopens a closed window and activates the app, and then hands the request to the live window. The tray depends on the value and that call, not on the window's models or templates.

A request sent while the window is closed waits in the router and is handed to the window that reopens. Only the last one waits. The window checks the request against what the network lists now: an item that is unknown, or has no server, is dropped and its place opens alone. `CommanderOpenRequest.init(page:server:)` maps each tray page that moved to its request, and returns nil for a page that stays in the tray.

Live work opens from the wall. Watch and Control name a worker by its resource, and their request is the Runs place with a remote-worker item: the window zooms the wall to the first hand-off tile that runs on that worker. A review's request is the Runs place with a review item. The wall has no review view of its own, so a review the network lists opens where the wall's own review row opens it, on Hand-offs. A worker no hand-off runs on, or a review that is no longer listed, opens the wall and zooms nothing. Request review stays in the tray: it is a composer, as Hand off and Consult are. The tray builds none of these requests by hand; it passes its page to `init(page:server:)`.

The request also says where it lands, in words. `CommanderOpenRequest.landingCrumbs` returns the breadcrumb of the place the request opens when its item exists. It takes the place from the same private mapping `destination(in:)` uses and the words from `LiveShell.navigation(...).crumbs`, read with every place listed and no workspace or run. A sender labels its link with these segments and keeps no table of its own, so the label and the landing can't drift.

## Hosting a relay from the app

The app starts and stops this Mac's relay through a GoF Adapter over the bundled `commander-relay` helper, the same shape as the `commander-network` adapter: positional arguments, no shell, one bounded JSON reply on stdout. `commander-relay host --json status|install|uninstall` answers `{"ok": true, "host": {...}}` with the host's state after the action, or `{"ok": false, "error": "..."}`. launchd stays the owner of the relay process, so the relay outlives the app and the helper is the only path that writes the launch agent.

`MultiplayerHostModel` is the one model for hosting, held by `MultiplayerModel` so the tray's Hosting page and the main window's toolbar show one state. A start loads the launch agent, then reads the status until the relay holds its lock (`running`) or the wait ends; a start that doesn't come up says where the relay's log is and keeps Stop available. Hosting needs only the relay helper, so it works when the network helper is missing. A Mac that was never set up starts from the same Start button: the page asks for the admin's email, and `host --json setup` fills the rest from the Mac (its name, Tailscale and `.local` addresses, and the Google Desktop client the network helper already uses) before installing.

## Remote relay deployment

A remote relay runs the same `commander-relay host` process as a Mac host. Only its supervisor differs: launchd on macOS, a systemd unit on Linux, or the Docker Engine for the container image. Each supervisor is an Adapter behind `hostmode.Install` and `hostmode.Uninstall`, selected at build time by operating system. The deploy tool, `commander-relay deploy`, owns only transport. It builds the artifact for the target's architecture, copies it over SSH and calls the target's own installer: `commander-relay host provision` for systemd, or the image's `init` and `configure` for Docker. It shares the SSH adapter in `hostkit` with the headless deploy. It never edits relay state, so a redeploy keeps the configuration, database and TLS identity, and clients keep their pin.

The tailnet option adds a Sidecar. Tailscale runs in its own container in userspace mode and forwards its tailnet port to the relay's loopback listener with `tailscale serve --tcp`; the relay stays unchanged and the two share only the host's loopback. The deploy tool adds the sidecar's names to the relay through `commander-relay host configure`, the relay's own command, so it still never writes relay state itself. On the device, the tailnet adapter is a Gateway over the local `tailscale` CLI: three tray verbs read status, start a login and list tagged peers. Adding a listed relay goes through the existing probe and pin confirmation, so discovery never grants trust.

## Headless Commander

The headless service is the same `agentctl serve` that runs beside the desktop app. Only its supervisor is new: a systemd user unit that runs as the SSH user, because the Claude sign-in, tmux sessions and checkouts belong to that user. The unit uses `KillMode=process`, so a restart for an upgrade stops only `agentctl` and leaves tmux and running workers alone.

Installed versions follow the same rule as ACP binary activation: each version unpacks into its own directory, and two symbolic links, `current` and `previous`, select one. An install moves `current` only after the binary is staged, then waits for `/v1/health` to report the new version. When it does not, the install moves `current` back and restarts the old version. Old directories stay until a later install prunes them, because a running worker may still use one. `/v1/health` reports the service's version and API version, which a deploying client compares with its own.

The systemd unit writer is shared with the relay's host mode. It lives in the dependency-free `agentcommander.network/hostkit` module, under `multiplayer/hostkit`, so both the root Commander module and the multiplayer module can import it. `hostmode` keeps only the relay's unit description. [Headless Commander](HEADLESS-COMMANDER.md)

A deploy from the Mac is a Pipeline of checked steps: connect, pick the release, download, verify the checksum and any attestation, upload, check API compatibility, run the doctor, install. Each step reports a result the way the tray's server probe does, and a failed required step stops the pipeline. The Mac only transports and verifies. It downloads the release, so the server needs no GitHub access or token, and it never edits the server's state: the installed `agentctl` on the server performs the install. That installed version, not the new one, runs the install, so a new binary that cannot start at all is still rolled back. SSH goes through the system OpenSSH client, which keeps host aliases, jump hosts and keys working. Release listing uses the signed-in `gh` CLI when there is one, so a private repository works with the user's own login. The SSH, release and systemd adapters live in `hostkit`, where the relay deploy reuses them.

## Tool details for the Pretty transcript

Full tool arguments, results, plan entries and thought times travel beside the console event, not inside it. This is a Claim Check: the console keeps its short preview, and the local app fetches the full record by tool ID or message ID. One boundary results. `ConsoleEvent` feeds run records, AG-UI snapshots, hosted clients and network hand-off, so none of them gains a value. `GET /v1/workers/{worker}/tool-details` answers only the local owner, and the hosted gateway does not route it.

A single ACP file location follows the same claim check and stays with the worker and call that supplied it. An omitted locations update preserves the last report. An explicit update with an empty, invalid or ambiguous location clears it. The Mac app checks the current local worker and canonical checkout before sending that file and the 1-based line as arguments to Xcode's line opener.

The runner sends details in the output batch, so the batch receipt makes a retry idempotent. The service keeps them in `tool-details/<worker>.jsonl`, outside `state.json`, with the latest 256 records or 16 MB per worker. One argument, result or content value is capped at 512 KB, even under "Keep everything as sent"; a cut value is listed in `truncated`. The transcript limit setting shortens string values and keeps JSON structure and key order. Full detail records carry bounded JSON Pointers for string cuts and an empty pointer for a whole-value cut in `shortened`. Older records and ambiguous or oversized path sets still carry the value-level flag. "Hide values that look like secrets" is stored by the service and applied by the app when it draws.

The app is the Claim Check's reader. `ToolDetailStore` holds one revision per worker and asks for summaries after it when that worker's transcript gains an entry or a call gains its result, never on a timer. Reads are serialized per worker, and each belongs to the call that makes it: a view's cancelled task cancels its own request and no other. A call that arrives during a read waits, and one further read serves every call that waited. The first of them makes it, so a cancelled read cannot take the latest transcript's page with it. A call that is cancelled while it waits leaves at once, without waiting for the read in flight, and one cancelled before it starts asks nothing. A waiting call whose service changed reads nothing. Each page carries the bounded set of retained keys, including unchanged details, so the reader can discard its copies of evicted records without another request. A cursor ahead of the service gets the full retained page at the service's revision. The app asks for a full record only when its line is opened. When a record is unavailable, the sentence uses its fallback wording. The four calls sit behind `ToolDetailSource`, so a view or a test never touches the socket.

An identified ACP plan snapshot keeps its exact item list behind the owner-only claim for its sequence, source cursor, turn and plan identity. The service takes these from the matching batch event, so a preview renumbered after restart cannot read an older checklist at the same sequence. The shared activity includes a digest scoped to its bound provider session, which lets Pretty replace the correct checklist and attribute a removal even when two plans share a turn.

The owner's reply to an ACP form request leaves a `form_outcome` record under the same claim check: the request ID as its Correlation Identifier, in the `form-outcome:` key namespace only the service writes, and the decision. Pretty draws "Answered a form" from that record alone, placed by its console sequence, so the line is the same after a restart and is never a local echo of the reply. The reply may bring no console event, so `ElicitationModel` raises one Event Notification when the service accepts a form reply, and `CockpitModel` answers with one read of that worker's details. The service stores the record under its lock before it answers, so one read holds it; if a read was already in flight, one more runs after it from the revision it returned. No timer or poll setting changes.

## Pretty conversation

Pretty reads a tool call as a sentence through a Strategy per tool family (`ActivityWords`): each supplies running, finished, fallback and failed wording and a summary phrase through one `ActivityWording` contract. `ActivityConversation.items` is a pure Composite step over the existing `ConversationItem`s: a group holds its lines, a line holds its original entries, and nothing is dropped. A result's renderer is chosen by a second Strategy, `ResultShape.select`, from the result's own properties after one Content Filter step unwraps MCP content and the network wrapper. The fixed denial table (`ActivityFailureWords`) is data in one place.

Three boundaries are new. Removing a queued follow-up is a Command to `POST /v1/workers/{worker}/messages/{message}/cancel`, owned by `CockpitModel.cancelFollowUp`; the message box only emits the message ID. Stop in the message box is the existing interrupt Command, not Stop worker. The transcript setting is read and written through the same `ToolDetailStore`, and the shown value moves only when the service accepts the change. Hiding secret-looking values stays a presentation rule in the app: it masks what is drawn, including Source, and never rewrites a record.
