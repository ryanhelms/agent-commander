# Agent Commander pattern decisions

Use this record before implementing each change. Begin with the user-visible behavior and the failure the design must prevent. Select a Gang of Four (GoF) pattern for a recurring collaboration between components, or an Enterprise Integration Pattern (EIP) for a message exchange with delivery consequences. A direct function, query, or state transition is also a design decision. [GoF catalog and applicability](https://www.informit.com/store/design-patterns-elements-of-reusable-object-oriented-9780201633610) · [Enterprise Integration Patterns catalog](https://www.enterpriseintegrationpatterns.com/patterns/messaging/)

The Go service owns domain operations. The native SwiftUI/AppKit cockpit, terminal client, Go CLI, and Go MCP server reach it through one versioned API. Go host helpers on macOS and Linux can execute work delegated to them under a run’s policy. The product serves one developer across a Mac and enrolled SSH hosts. Each row names the component responsible for the behavior. Milestones M1–M6 follow the [MVP plan](../MVP-PLAN.md).

## First usable run

After visual approval, start with the local Mac and one supported provider. Have a coordinator delegate a real task through MCP, watch its live tmux worker and answer a question from the cockpit through the API. Add a second worker on the same path to exercise the live wall while replying to the first. Use this version for a real task as soon as the reply reaches the intended worker and request exactly once under a repeated click, and typing resumes at the expected keyboard target. If delivery is uncertain, show that status and keep the original reply available for reconciliation.

Use what happens in that session to choose the next increment. A second provider, broader adoption, saved views, SSH continuity, Git integration, and historical search can each be added and exercised when their flows are ready.

## Before coding a change

The 15 flow decisions below already provide the pattern analysis. Before writing code, consult the row that applies. Use its decision directly when it fits. For a new flow or a change of approach, one sentence in the current work item can name the choice and the problem it solves. For example, “Bind replies to the question ID so changing focus cannot redirect an answer.”

## Adoption status

- **Use as the corresponding flow ships.** The GoF Facade, Adapter, Command and identity-resolution Strategy correspond to actual API, provider, retry and repository variations. EIP Request-Reply, Correlation Identifier, Idempotent Receiver, Publish-Subscribe Channel and Message Store describe MVP delivery and persistence guarantees. Atomic Design organizes the app’s component inventory. The direct policies and state transitions identified below also ship in the MVP.
- **Conditional within the MVP.** Apply EIP Process Manager to adoption or integration when asynchronous replies and branching participants require a coordinator. Use a Messaging Gateway where a domain caller needs to abstract a real messaging boundary. Reassess GoF State, Composite or additional Strategies only when a row’s trigger appears.
- **Deferred.** An external broker, replay of the entire event history to reconstruct domain state, and distributed transaction coordination each require independent evidence that the per-user service cannot meet a measured need.

## Host, provider, and worker boundaries

The independently released `agent-acp` SDK generates a GoF Facade for each supported language from its versioned session schema. Each facade delegates runtime calls to an adapter. This supplies one vocabulary for conversation operations. Provider Adapters translate its messages, request IDs and events into the protocol supported by each harness. Share the ACP transport implementation across adapters. Define the public contract in portable session terms so transport negotiation and provider-specific history readers can change independently of callers. Commander maps worker IDs to session handles and applies its ownership policy before invoking the facade.

## Streams, history, and Git

The local cockpit feed uses a GoF Adapter and EIP Message Translator to project retained provider events as AG-UI messages. A Publish-Subscribe Channel signals committed workspace changes over the private socket. Each subscription starts with a current snapshot and sends ordered state patches. Reconnection replaces the projection with a fresh snapshot. Reply commands keep their existing Request-Reply path and Correlation Identifier.

The local Claude adapter uses a stable provider session ID and passes each follow-up through standard input. The service uses an addressed inbox as a Message Store. The receiver claims a follow-up by its Correlation Identifier under the current control generation. A caller-provided idempotency key returns the same acceptance receipt after a retry. Handoff cancels queued commands from the outgoing controller. A restart marks a claimed turn with an uncertain outcome until the original runner reports evidence. The original runner can report the outcome using the same message ID.

Console and Pretty share that feed. The cockpit keeps a display mode per worker ID so zoom, the wall and PiP agree even when a new snapshot replaces the worker object. Selecting a mode for all consoles sets the default and clears individual choices.

The cockpit keys persistent accent preferences by harness identity. A color change follows that harness across workers, runs and windows. Attention and keyboard focus retain their own cues.

## Optional coordinator companions

The local provider adapter discovers the Devflow UI companion through a bounded MCP tool listing in the run’s checkout. It registers the companion for a coordinator only when the restricted server advertises exactly `devflow_ui_open`. Only the coordinator’s live connection requests an automatic browser open. The discovery probe has no browser side effects. A missing executable, an older release, or a broader tool surface leaves the planning run available with its usual permissions. The service owns executable selection and passes the verified path through the private launch file. The live companion receives the socket, actor ID, scoped token and coordinator role from that job. The discovery process receives no actor binding. Commander enforces the token’s permissions on each worker activity or reply request.

## Local SDK runtime

The tmux runner calls the SDK Facade for each new opted-in assignment. Its private launch record fixes the runner choice. The worker receives a scoped MCP connection. Only the trusted local runner binds a native session ID to a worker, and an existing binding is immutable. The input lease and the provider request ID address each reply. The API treats a repeated operation ID as an Idempotent Receiver and validates its intent.

Delegation accepts an optional client and falls back to the run's client. The launcher checks availability before the service reserves the worker and persists its selected client. The pinned Codex ACP adapter marks session roots trusted and merges effective MCP configuration. An isolated home alone leaves the checkout configuration in scope. Enabling managed Codex requires a launch profile that can enforce the run's tool policy before entering the requested checkout.

For the first SSH-only run, keep the controlling runner beside Commander's service and transport the remote harness's ACP stream over SSH. Give the remote MCP process a reverse Unix socket to a worker-authenticated listener. That listener requires the worker credential for all requests before executing an API operation. The desktop owner socket stays local. Use a fresh remote socket for each connection and rely on OpenSSH host-key verification. A loopback OpenSSH fixture with generated keys verified the live Claude worker, its authenticated MCP round trip, and the local and remote labels in the native cockpit. Passive history reads invoke the host-side SDK reader over a separate SSH connection using the original native handle. [SSH verification](verification/ssh-worker.md)

For SSH-only disconnects, keep the native session reference and pending question in the existing Message Store. An answered request keeps its original answer and correlation identifier, with a separate delivery status when the adapter cannot confirm receipt. The Idempotent Receiver returns the original reply receipt on an identical retry. Reconciliation correlates the exact wait invocation and its recorded MCP result in the original native history. It can confirm receipt of the same answer or preserve the unknown outcome. It leaves the original turn disconnected.

A disposable Codex 0.171.0 profile with the checkout explicitly marked untrusted still launched a synthetic MCP executable from that checkout on `session/new` through codex-acp 2.9.0. The fixture used a synthetic credential and sent no model prompt. Keep the managed Codex gate until the replacement path passes the same check with the checkout process absent and the scoped Commander MCP server available.

The same version of native Codex App Server passed that checkout test when called directly. With a dedicated Codex profile, the checkout marked untrusted, apps and plugins disabled, and an explicit MCP server in `thread/start`, the scoped fixture process ran and the checkout process did not start. App Server reported a read-only sandbox and approval policy `never`. Before adopting this path, verify inherited host configuration and native authentication and replay, then exercise the mixed run through the existing SDK facade. [Project configuration loading](https://github.com/openai/codex/blob/main/codex-rs/config/src/loader/mod.rs)

The native provider regression runs with `AGENT_COMMANDER_TEST_CODEX_POLICY=1 go test ./internal/provider -run TestCodexNativeCheckoutIsolation`. It also shows that an MCP server configured in the dedicated profile still launches even with the checkout explicitly untrusted. A separate disposable test used the pinned ACP adapter's `CODEX_PATH` hook to put a policy bridge in front of App Server. Through ACP `session/new`, the bridge set the native session to read-only, kept the checkout untrusted and passed the one requested MCP server. Only that fixture server started. This proves the adapter can use a bridge at session creation. A production bridge still needs to enforce the same policy for turns and resumed sessions and validate that the native profile and host layers supply no extra tools.

Native readers supply a passive history Adapter for each harness. The service queries it outside the command lock and reconstructs a bounded in-memory view. An arriving live update takes precedence over a stale read. A historical permission is display-only. Commander keeps its own assignments, operation receipts, reported results and pending inputs.
