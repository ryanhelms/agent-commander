# Native console source inspector

Claude Fable 5.2 implemented the Swift inspector in an isolated worktree using the original wall, focused worker, and PiP concepts. It reuses the existing console display menu and worker action list. The same inspector is wired into Console and Pretty. The compact PiP action opens the addressed worker's inspector. [Component map](../../system/ATOMIC-DESIGN.md)

Codex ran the native Linux QA app against a real local Commander service with two deterministic ACP workers, Copper and Maple. macOS Accessibility opened Copper's existing worker action list and selected **Inspect source**. The Provider tab returned only Copper's Pi fixture tool result. The Live tab showed Copper's original ACP tool input and completed result. The Journal tab showed an explicit gap because the generic ACP profile has no supplementary vendor-journal reader. [Provider history](wall-provider.png) · [Live ACP source](wall-live.png) · [Journal gap](wall-journal-gap.png)

Compared with the approved wall, the inspector anchors to the existing title bar. It adds a temporary 520 × 540 point popover and leaves the direct console layout in place when closed. The QA fixture has two worker tiles. The approved composition shows five workers and a nested group. [Original wall](../../concepts/coordinator-wall.png)

Codex switched the native app to Pretty through its existing display menu, focused Copper, and opened the inspector. The live ACP source contained Copper's fixture records. Maple's records stayed scoped to Maple. The focused view retained its coordinator split, worker breadcrumb, and footer. The inspector opens below the existing display control and overlays the right edge of the focused console. [Focused Pretty capture](focused-pretty.png) · [Original focus](../../concepts/focused-worker.png)

With Maple focused, Copper opened an ACP permission request. Its floating PiP kept the amber attention treatment, original request ID, and inline reply field. The PiP display menu's **Inspect Source in Worker** action focused Copper and opened Copper's live source. The local service still recorded Copper's original request as pending afterward. The QA capture shows a single floating request. The approved concept shows two requests stacked over the wall. [Floating PiP](pip-request.png) · [PiP destination](pip-destination.png) · [Original PiP](../../concepts/attention-pip.png)

With SDK 0.1.5, native Pretty, Console, and PiP show the completed fixture tool as done. The live source still contains the original pending and completed ACP updates. The popover extends beyond the right edge of the focused window.

A second isolated run used the real Pi translator and stock Antigravity CLI. In both display modes, macOS Accessibility found the synthetic file marker in Pi's Provider source and the file tool in Antigravity's Live ACP source. Both inspectors used the same worker actions and tabs as the fixture. The Pi popover overlapped the middle of the two-worker wall, and the Antigravity popover extended past the right edge of the app window. Provider records with dense JSON occupied several rows of scrollback, including in Pretty. Compared with the approved concepts, the captures retain the coordinator split and show the existing console disclosure row and source popover. ## Pi after a service restart

The real Pi CLI read a missing file and a 4 × 4 PNG using its file tool and separately installed ACP translator. The model ran on loopback. An isolated native QA app connected to the restarted Commander service built with SDK 0.1.9. The native Provider history loaded 12 records on its first page and 21 after **Load more**. The coordinator occupied the left pane of the wall. This fixture's coordinator performed the reads directly, leaving the worker wall empty. [Pi recovery probe](../pi-rpc/verify.py) · [Original wall](../../concepts/coordinator-wall.png)

In Pretty, expanding the failed read revealed the original `ENOENT` for `missing-swatch.txt`. Expanding the successful read showed the PNG description. Opening its retained `pi.message` under **Inspect Source → Provider → Show the original record** exposed `toolCallId = call_swatch_read`, MIME type `image/png`, the complete base64 field and the decoded inline image. In Console, the Provider inspector showed the same tool IDs, failed and completed statuses, original error and PNG bytes. The restarted service’s incremental workspace snapshot contained 21 messages. The separate Swift recovery test checked the dimensions and exact bytes in both display projections. [Native byte and dimension check](../../../Tests/AgentCommanderTests/PiRecoveryTests.swift)

The debug build initially showed an empty Console scroll area below the assignment. Switching modes and scrolling revealed the transcript. After opening the main Console swatch disclosure, this QA process stopped answering accessibility and screenshot requests and used about 94% of one CPU core. Two process samples identified repeated SwiftUI layout work. The stored Pi data and the independently running service remained available.
