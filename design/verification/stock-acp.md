# Stock ACP executable verification

On November 23, 2026, a fresh Commander service launched Antigravity CLI 1.5.13 through an owner-registered profile. The profile supplied the installed executable and the arguments `acp --disable-telemetry --include-default-customizations=false`. Commander selected the profile through `agentctl run --client agy`. The service, tmux server and checkout used isolated temporary directories.

The synthetic task asked the CLI to read one local file and use Commander's question tools. Commander bound the native session, displayed the ACP permission requests for the test ask and wait calls, and accepted their one-time approval options. The owner answered the resulting Commander request by its exact ID with a literal dollar sign in the reply. The worker finished and reported three completed tool calls. Its assistant output contained both the marker read from the file and the exact owner reply.

The installed Gemini CLI also reached ACP `session/new` through the same configuration path. Its upstream service rejected the installed client for the signed-in Gemini Code Assist account and directed it to Antigravity. Antigravity supplied the successful stock-ACP execution evidence.

An independent Node application used the locally installed CopilotKit connector. It approved the scoped ACP permissions, sent the addressed answer, and observed tool-role messages. The worker's live source records retained the file-read, ask and wait call identities, names, inputs and completed statuses. Antigravity omitted both ACP `content` and `rawOutput` from those completed updates. The marker and reply belong to the assistant output in this run. A repeat of the combined prompt accepted the one-time ask permission and the addressed answer, then exceeded the observation deadline before completing.

A focused file-read run completed through the installed connector. The live source and AG-UI tool message carried the same file-read call identity. Reconnecting with the original run and operation IDs recovered that tool record and the completed operation. The assistant returned the exact file marker. The stock tool message carried the read classification.

Computer Use found the file tool in Antigravity's Live ACP source in native Console and Pretty. [Native verification](native-source/README.md)

An independent ACP v1 client also tested the installed agent's advertised `session/list`. Antigravity 1.5.13 returned 13 entries when the client supplied a newly created, empty working directory. The probe recorded only the count. The protocol defines this parameter as a filter on the session's primary working directory. [ACP session listing](https://agentclientprotocol.com/protocol/v1/session-list)

The same installed Antigravity executable returned zero visible records through Commander’s 0.1.10 SDK for a fresh empty workspace. Claude, Codex and the independently installed Pi translator also returned zero. The SDK checks each listed session’s primary directory before returning its identity and counts only eligible rows toward the caller’s page limit. A separate mixed-directory regression completed multiple pages and verified that in-scope sessions remain discoverable. [Installed compatibility matrix](sdk-release/compatibility.json)

Antigravity 1.5.13 advertised ACP `loadSession` in its initialization response. A fresh ACP process loaded a completed disposable conversation by its original session ID and working directory, with an empty MCP server list. It replayed seven updates, including the synthetic file marker in assistant text and the completed file-read call. The replay still omitted both `content` and `rawOutput` from the tool record. This confirms a standard way to retrieve the retained conversation, with the same tool-body gap as live ACP. [ACP session loading](https://agentclientprotocol.com/protocol/v1/session-setup#loading-a-session)

With SDK 0.1.5 and `history.format` set to `acp-v1-replay`, Commander returned a typed gap while the completed worker could still resume. After the owner stopped the worker, four two-record pages delivered the original prompt, the completed file call, its raw input and the actual assistant output under the original native identity. No page contained an actionable permission. After a full Commander restart, the worker's console started empty and the workspace subscription recovered the retained messages. Computer Use opened Provider history from the stopped Antigravity worker in Console and Pretty. The approved wall shows a working group with a live request. The archive capture shows a single stopped worker and the shared Provider inspector. The 0.1.12 SDK candidate repeated the real Antigravity 1.5.13 file-read workflow. A new worker returned the undisclosed file marker in assistant text. After stopping the worker, four two-record pages recovered the original session ID, prompt, tool input, completion status and assistant text. A fresh Commander service projected the recovered call and text. This adapter omitted the file result body from its completed call.
